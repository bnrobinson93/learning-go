Adapters and Method Sets

Your League has a Ranking method and Ranker wants a Ranking method, and yet the compiler says no. Here is the rule it is enforcing, and the two shapes Go gives you for getting around it without touching League.

01The failure

This is the code from ch7/main.go, reduced to the part that matters:

type TeamName string

func (l League) Ranking() []TeamName { … }

type Ranker interface {
	Ranking() []string
}

RankPrinter(league, os.Stdout) // League does not implement Ranker

A type satisfies an interface when its method set contains a method with the identical name and signature. Not a compatible one — an identical one. Go has no covariance: []TeamName in the return position is a different signature from []string, so League.Ranking is simply a different method than the one Ranker asked for. (Spec: Method sets)

The rule

Implementation in Go is structural but exact. Same name, same parameters, same results — or the type does not implement the interface. There is no partial credit and no adaptation step built into the language.

02The shortcut that isn't

The obvious repair is to hand back the same slice under a new name. It does not compile:

func (l League) Ranking() []string {
	names := …            // []TeamName
	return []string(names) // ✗
}

cannot convert names (variable of type []TeamName) to type []string

TeamName and string convert freely — they share an underlying type. []TeamName and []string do not, because a slice conversion requires identical element types, not merely convertible ones. The two slices have different element types, therefore different memory interpretations, therefore no conversion. (Spec: Conversions)

So the copy is unavoidable. That copy loop is the whole substance of your adapter — the question is only where to put it.

03Shape one: the wrapper type

An adapter is a new type that wraps an existing one and presents the method set some interface demands. Embed League so the wrapper keeps everything League already does, then declare the one method whose shape you need to change:

type LeagueRanker struct {
	League
}

func (l LeagueRanker) Ranking() []string {
	src := l.League.Ranking() // the original, called explicitly
	out := make([]string, 0, len(src))
	for _, n := range src {
		out = append(out, string(n))
	}
	return out
}

RankPrinter(LeagueRanker{league}, os.Stdout) // ✓

Two things are happening. Embedding promotes League's fields and methods onto LeagueRanker, so MatchResult and Wins still work through the wrapper. And the method you declare directly on LeagueRanker is at depth zero, so it shadows the promoted Ranking — which is why you must write l.League.Ranking() in full to reach the original. (Effective Go: Embedding)

Trap

Do not reach for type LeagueRanker League instead. A defined type declared from another defined type starts with an empty method set — it copies the structure, not the behaviour:

a.Ranking undefined (type LeagueAlias has no field or method Ranking)

04Shape two: the function adapter

When the interface has exactly one method, you can skip the struct entirely. Give a function type a method, and any function of that shape becomes an implementation. This is the shape you reached for — the piece that was missing is the method:

type RankerAdapter func() []string

// Without this line, RankerAdapter satisfies nothing. A func type
// has an empty method set until you give it one.
func (f RankerAdapter) Ranking() []string { return f() }

func (l League) RankingStrings() []string {
	out := make([]string, 0, len(l.Wins))
	for _, r := range l.Ranking() {
		out = append(out, string(r))
	}
	return out
}

err := RankPrinter(RankerAdapter(league.RankingStrings), os.Stdout)

The last line is doing something worth slowing down for. league.RankingStrings — written without parentheses — is a method value: a func() []string with the receiver league already bound into it. Its type matches RankerAdapter's underlying type, so it converts, and the converted value carries Ranking in its method set. (Spec: Method values)

This is not a trick — it is how the standard library adapts plain functions into http.Handler, via http.HandlerFunc.

Prefer the wrapper when the adapted thing has state and other behaviour worth carrying along. Prefer the func adapter when the interface has one method and you just need to hand over one piece of behaviour.

05The two near-misses

Both drafts were one step away, and both stalled in the same place: a method got attached to the wrong type, or to no type at all.

What was writtenWhy it satisfies nothing
type RankerAdapter string Adapters wrap the thing that has the behaviour. It lives on League, so a bare string has nothing to delegate to.
func (t Team) Ranker() string Named after the interface instead of after the method it must provide, on the wrong receiver, with the wrong result type.
type RankerAdapter func() []string
with no method on it		 Right type, no method set. A defined func type implements nothing until you declare Ranking on it.
func (l League) RankerAdapter() []string The conversion body is correct — but named for the adapter type rather than for what it does, and hung on League, where Ranker never looks for it.

06Check yourself

Answer before scrolling back. Getting one wrong here is more useful than getting it right by re-reading.

Why does League fail to satisfy Ranker?

Method sets are matched by exact name and signature. []TeamName and []string are different result types, so these are two unrelated methods that happen to share a name.

What does return []string(names) do, where names is a []TeamName?

Slice conversion needs identical element types. TeamName converts to string; []TeamName does not convert to []string. You must copy element by element.

After type LeagueRanker League, what does the new type have?

A defined type gets its underlying type's structure and an empty method set. That is why the adapter embeds League in a struct instead — embedding promotes the methods.

In the http.HandlerFunc pattern, what lets a plain function satisfy an interface?

Methods may be declared on any defined type in the same package, including a func type. The method set of RankerFunc then contains Ranking, so any function of that shape satisfies Ranker.

07Do this next

You have the func adapter working. Now write the other one — the LeagueRanker struct from section 3 — in the same file, and call RankPrinter once with each. Holding both shapes in the same program is what makes the choice between them concrete rather than theoretical.

Then push on it: make the adapter print each team's win count beside its name. Notice that neither League nor Ranker has to change to allow it. That is the real point of the pattern — the adapter is where the mismatch between two designs is allowed to live, so neither design has to bend.
