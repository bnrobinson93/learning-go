Pointer and Value Receivers

Your League already mixes both: MatchResult takes *League, Ranking takes League. That mix is fine — but it decides which values can satisfy an interface, and it hides a bug that half-works.

01Two rules, doing different jobs

People conflate these constantly. They are separate, and only the second one is about interfaces.

Rule A — calling a method (a convenience)

If a variable is addressable, Go inserts & or * for you. So this compiles even though the receiver is *League:

league := League{…}
league.MatchResult("Cowboys", 1, "Broncos", 2)
// rewritten by the compiler as (&league).MatchResult(…)

Addressable means: a variable, a pointer dereference, a slice element, or a field of an addressable struct. Not addressable: a map element, a function's return value, or a composite literal. Those fail:

Team{}.AddPlayer("x")     // ✗
teamsByName["a"].AddPlayer("x") // ✗

cannot call pointer method AddPlayer on Team

Rule B — method sets (the real rule)

The convenience above does not apply to interface satisfaction, because an interface value has no address to take. (Spec: Method sets)

TypeMethod set contains
Tmethods with receiver T only
*Tmethods with receiver T and *T
The consequence

If any method an interface requires has a pointer receiver, only *T satisfies that interface. A T value never will — no matter that you can call the method on a T variable directly.

02Where this bit your adapter

RankerStruct embeds League by value. Promotion carries the method sets along with the same asymmetry, so MatchResult lands on *RankerStruct and not on RankerStruct:

var _ interface{ MatchResult(…) } = RankerStruct{} // ✗
_ = RankerStruct{}.MatchResult                     // ✗

RankerStruct does not implement … (method MatchResult has pointer receiver)
cannot call pointer method MatchResult on RankerStruct

Yet rs.MatchResult(…) on a variable compiles fine — Rule A rescued it. That gap between "I can call it" and "it implements the interface" is the single most common Go surprise.

Embedding the pointer instead puts both receiver kinds into the value's method set, and stops the wrapper copying anything:

type RankerStruct struct {
	*League // embedded — no field name, no colon
}

03The bug that half-works

Copying a struct is shallow. A copied League gets its own Wins field, but that field is a map header pointing at the same hash table. So mutations through the copy are visible; reassignments are not. Verified output:

rs := RankerStruct{league}          // League embedded by value

rs.MatchResult("Cowboys", …)        // l.Wins[name]++
league.Wins → map[Cowboys:1]        // ← the original DID change

rs.Reset()                          // l.Wins = map[TeamName]int{}
league.Wins    → map[Cowboys:1]     // ← unchanged
rs.League.Wins → map[]              // ← only the copy was reset
The rule worth memorising

Mutating through a reference field (map write, slice element write) crosses the copy. Reassigning the field itself does not. This is why the failure mode is "some updates land and some vanish" rather than an honest crash.

04The same trap in a for loop

You have Teams []Team, so you will meet this one next. The loop variable is a copy of the element:

for _, t := range l.Teams {
	t.AddPlayer("Brad") // mutates the copy, then throws it away
}
// l.Teams[0].Players → []
for i := range l.Teams {
	l.Teams[i].AddPlayer("Brad") // slice element is addressable
}
// l.Teams[0].Players → [Brad]

05So which receiver do I write?

SituationReceiver
The method mutates the receiver*T — required
The type has a mutex or other non-copyable field*T — required
Some methods on the type already use *T*T — be consistent
Small, immutable value type (time.Time-ish)T

Consistency is the actual guidance: Go Code Review Comments says don't mix receiver kinds on one type. Your League mixes them, which is exactly why the interface question got confusing. Making Ranking take *League too would be the idiomatic cleanup — note that it would then break RankerStruct{league} at compile time rather than silently.

06Check yourself

A type T has one method, with receiver *T. Which values satisfy an interface requiring it?

The method set of T holds only value-receiver methods. Addressability lets you call the method on a variable, but it never changes what T implements.

Why does m["a"].AddPlayer("x") fail when AddPlayer has a pointer receiver?

Go can only auto-insert & for addressable operands. Map elements are not addressable — the table may move them — so the compiler has nothing to take the address of.

rs holds a copy of league. rs.MatchResult(…) runs l.Wins[name]++. What does league.Wins show?

Copying the struct copies the map header, not the table. Both structs reference one table, so writes through either are visible to both. Reassigning l.Wins wholesale would not cross the copy.

Which of these operands is addressable?

Slice elements live in a backing array at a stable address, so teams[0].Method() works with a pointer receiver. That is why the index-based loop fixes the range-copy bug.
